Base64 Encoder & Decoder

Convert text to Base64 and back. UTF-8 safe, so emoji and non-Latin characters survive the round trip.

What Base64 actually is

Base64 is a way of representing arbitrary binary data using only 64 printable characters: A–Z, a–z, 0–9, + and /. Every 3 bytes of input become 4 characters of output, so the encoded form is about 33% larger. It is not encryption and it is not compression — it is a transport encoding, used where only text can travel.

Why the standard version breaks non-English text

The classic JavaScript approach — btoa(text) — only accepts characters in the Latin-1 range. Feed it Chinese, Arabic, Cyrillic or an emoji and it throws InvalidCharacterError, or silently produces the wrong bytes. This tool encodes to UTF-8 first and only then applies Base64, and reverses that order when decoding, so any character round-trips correctly.

When you need it

  • Embedding data in HTML or CSS — small images and fonts are often inlined as data: URIs.
  • HTTP Basic authentication — the header is the username and password joined with a colon and Base64-encoded.
  • JWT inspection — a JSON Web Token's first two segments are Base64URL-encoded JSON. Decoding them is how you read the payload.
  • Passing binary through a text channel — email attachments, XML payloads, configuration values.
  • API keys and secrets in transit — although note that Base64 offers no protection at all.

Base64 vs Base64URL

Standard Base64 uses + and /, both of which have meaning inside a URL. Base64URL substitutes - and _ so the result can be placed in a query string or a filename. JWTs use Base64URL, which is why the strings you paste from a token sometimes contain dashes and underscores. This tool accepts either form when decoding, and the checkbox controls which form it produces.

FAQ

Is Base64 a form of encryption?

No. Anyone can decode Base64 in a fraction of a second, with no key. Never use it to protect a password or a secret.

Why is the encoded text longer than the original?

Each group of 3 bytes becomes 4 characters, so the output is roughly 133% of the input size. That overhead is the price of restricting the output to printable characters.

Why does my decoded text look like garbled characters?

The bytes are probably not UTF-8 — they may be an image, a compressed blob or text in a different legacy encoding. Decoding binary as text always produces something, but it is rarely meaningful.

Is anything sent to a server?

No. Encoding and decoding use the browser's built-in btoa, atob, TextEncoder and TextDecoder. Nothing leaves the page.

JWT Decoder

Paste a JWT to read its header and payload, see exactly when it expires, and understand what each claim means.

What a JWT actually is

A JSON Web Token is three Base64URL-encoded strings joined by dots:

header . payload . signature

  • Header — JSON describing the token: which algorithm signed it (alg) and which key was used (kid).
  • Payload — JSON holding the claims: who the user is, what they may do, and when the token expires.
  • Signature — a cryptographic seal over the first two parts, made with a key only the issuer has.

Base64URL is just Base64 with two characters changed so the result is safe inside a URL. It is an encoding, not encryption — which is the single most important thing to understand about JWTs.

The payload is readable by anyone

Because the first two segments are only encoded, anyone holding the token can read every claim inside it. Intercept it, or just paste it here, and the contents are plain. Never put a password, an API key, a national ID number or any other secret in a JWT payload. The signature prevents tampering, not reading.

That is also why a JWT must only travel over HTTPS, and why it should be stored where script cannot read it if your threat model includes cross-site scripting.

Why decoding is not verification

This tool — and every online decoder — can only read the token. Verifying it means recomputing the signature with the issuer's secret or public key and comparing. Without that step, a decoded payload is worthless as evidence: an attacker can trivially construct a token with "role":"admin" and no valid signature at all, and any server that trusts the payload without checking the signature will hand over the account.

That failure has a name — the alg:none attack — and it remains common enough to be worth knowing: a server that reads the alg header from the token itself, rather than fixing the expected algorithm, can be told to expect no signature at all.

Reading the timestamps

Three claims carry Unix timestamps in seconds: iat (issued at), nbf (not before) and exp (expires at). A server must reject a token whose exp is in the past, and one whose nbf is in the future. A token with no exp at all is a common and serious misconfiguration — it is valid forever if it leaks.

Short lifetimes are the point: access tokens of 5–60 minutes limit the damage from a stolen token, with a separate long-lived refresh token used to obtain new ones.

FAQ

Is my token sent to a server?

No. Decoding is Base64URL plus JSON.parse, both of which run in this tab. That matters more than usual here — a JWT is a live credential, so pasting one into an unknown decoder is a real risk. This page keeps it local, and you can verify that by disconnecting from the internet before pasting.

Can I get the original values back from the signature?

No. The signature is a one-way hash of the header and payload. It cannot be reversed, and it does not contain the key.

What if the token has five parts?

Five segments means it is a JWE — JSON Web Encryption, where the payload really is encrypted. A decoder like this one cannot read it without the decryption key.

Is it safe to paste a production token here?

The decoding happens locally, but a token is still a credential. Prefer a token from a development environment, and treat any token you have pasted anywhere as worth rotating.
